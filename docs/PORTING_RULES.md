# SmartMoving 1:1 포팅 완전 규칙서

> 이 문서를 처음부터 끝까지 따르면 1:1 번역이 자동으로 완수된다.
> 이전 작업에서 발생한 모든 누수 원인을 분석하여 구조적으로 차단한다.

---

## 0. 왜 이 문서가 필요한가 — 이전 실패 원인 분석

| 실패 패턴 | 구체적 사례 | 이 문서의 대응 |
|-----------|------------|---------------|
| C 항목이 파일 단위로 너무 굵어서 내부 세부 기능이 묻힘 | `C-01: SmartMovingClimber 구현` 하나로 15개 기능 은닉 | **원자 단위 분해 규칙** — 항목 하나 = 동작 하나 |
| `// TODO Phase N`이 추적 없이 코드에 남음 | `climbBackJump`, `wantClimbUp` 등 30여 개 | **즉시 등록 규칙** — TODO 작성 = 동시에 C 항목 등록 |
| `[미확인]` 주석이 코드에서 끝남 | `_freeClimbingUpSpeedFactor` 등 미확인 상수 | **미확인 즉시 차단 규칙** — 미확인 상태로 C 항목 완료 불가 |
| "스켈레톤 존재 = 완료"로 처리 | `tickEssential()` 빈 메서드, no-op 핸들러 | **완료 정의** — 바디가 비어있으면 완료 불가 |
| 구현 중 발견한 신규 누락이 역류 안 됨 | 구현하다가 발견한 세부사항이 주석으로만 기록 | **역류 규칙** — 구현 중 발견 즉시 C 항목 삽입 |
| 완료 후 검증 없음 | `[x]` 처리 후 코드에 TODO 다수 잔존 | **완료 전 의무 검증 체크리스트** |

## 1. 핵심 원칙 (절대 원칙)

```
원칙 1. 원자 단위 원칙
   C 항목 하나 = 원본의 동작 하나.
   "클래스 구현", "기능 구현" 같은 복수 동작을 포함하는 항목은 금지.

원칙 2. 완전 추출 원칙
   리서치 단계에서 원본 클래스의 모든 메서드 × 모든 분기 × 모든 상수를
   빠짐없이 추출해야 한다. 기록되지 않은 동작은 구현 대상이 아니다.

원칙 3. 추적 가능성 원칙
   코드에 TODO / [미확인] / 빈 메서드가 존재하는 순간,
   해당 항목은 반드시 PENDING_RESEARCH.md에 C 항목으로 등록되어 있어야 한다.
   추적되지 않는 TODO는 버그다.

원칙 4. 미확인 차단 원칙
   설계 근거가 없으면 구현하지 않는다.
   "아마 이럴 것이다"로 코드를 작성하는 순간 1:1 번역이 깨진다.

원칙 5. 완료는 검증 이후 원칙
   C 항목을 [x]로 바꾸기 전에 완료 검증 체크리스트를 반드시 통과해야 한다.
```

## 2. 용어 정의

| 용어 | 정의 |
|------|------|
| **원자 동작** | 입력 → 처리 → 출력이 하나인 최소 단위. if 분기가 있으면 분기당 하나의 원자 동작. |
| **C 항목** | PENDING_RESEARCH.md에 등록된 구현 단위. 항상 원자 동작 하나와 1:1 대응. |
| **리서치 문서** | docs/research/original/ 아래의 원본 분석 파일. |
| **설계 근거** | 리서치 문서에 기록된 원본 동작 설명. 이것 없이는 코드 작성 불가. |
| **미확인** | 1.21.1 API 이름, 원본 상수값, 동작 방식 중 하나라도 확인되지 않은 상태. |
| **누수** | 원본에는 존재하지만 포팅 코드에 대응물이 없는 동작. |

## 3. 리서치 단계 규칙

### 3-1. 리서치 문서 완전성 기준

리서치 문서는 아래 항목이 **전부** 기록되어야 완전하다고 간주한다.

```
클래스당 추출 의무 목록:
□ 모든 public 메서드 — 시그니처 + 전체 분기 로직
□ 모든 private 메서드 — 시그니처 + 전체 분기 로직 (public에서 호출되는 것)
□ 모든 상수 (static final) — 이름 + 값 + 사용처
□ 모든 필드 — 이름 + 타입 + 초기값 + 갱신 조건
□ 모든 if/else 분기 — 조건 + 각 분기의 동작
□ 모든 루프 — 반복 조건 + 반복 동작
□ 외부 호출 — 어떤 메서드를 호출하고 결과를 어떻게 사용하는지
□ 호출 타이밍 — 이 메서드는 어느 시점에 누가 호출하는가
```

> **체크 방법**: 리서치 문서의 행 수 ≥ 원본 소스의 비공백 행 수 × 1.5
> (설명이 코드보다 짧으면 설명이 불완전하다)

### 3-2. 리서치 완료 조건

리서치 청크를 완료로 처리하기 전:

```
□ 원본 파일의 모든 메서드가 리서치 문서에 섹션으로 존재한다
□ 각 메서드의 모든 if 분기가 기록되어 있다
□ 모든 상수/매직넘버의 값이 기록되어 있다
□ "확인 필요" / "미확인" 항목이 있다면 PENDING_RESEARCH.md A 항목에 등록했다
□ 1.21.1 매핑이 불명확한 항목에 [미확인] 표시 + A 항목 등록을 했다
```

### 3-3. 리서치에서 C 항목으로 변환하는 규칙

리서치 완료 후 C 항목 등록 시:

```
변환 단위:
- 메서드 하나에서 if-else가 n개이면 → C 항목 최소 n+1개
- 메서드 여러 개가 한 흐름을 형성하면 → 흐름당 C 항목 하나 (단, 내부 분기는 세분화)
- 상수 하나가 독립 동작에 영향을 미치면 → 별도 C 항목

금지:
- "A 클래스 전체 구현" → 금지
- "A 기능 구현" (내부에 3개 이상의 원자 동작 포함) → 금지
- "TODO 해결" → 금지 (무엇을 해결하는지 명시해야 함)

허용:
- "isClimbing=true일 때 fallDistance를 0으로 리셋"
- "setCrawling(false) 호출 시 crawlingCooldown=10 설정"
- "travel() HEAD에서 isClimbing 상태면 ci.cancel() 실행"
```

## 4. C 항목 형식 규칙

### 4-1. C 항목 필수 구성 요소

```markdown
| C-N | [원자 동작 설명 — 주어+동사+목적어 형식] | [의존 항목] | [ ] |
```

**원자 동작 설명 규칙:**
- 주어: 어느 조건/상태에서
- 동사: 무엇을
- 목적어: 어떤 값으로/어떻게

**좋은 예:**
```
isClimbing=true 동안 매 틱 fallDistance를 0으로 리셋
travel() 진입 시 SM 활성 상태이면 vanilla 코드를 ci.cancel()로 차단
wantClimbUp 키 입력 시 verticalClimbSpeed를 +0.2로 설정
```

**나쁜 예 (금지):**
```
클라이밍 구현          ← 너무 굵음
TODO Phase 9 처리     ← 무엇인지 불명확
SmartMovingClimber 이식  ← 파일 단위
```

### 4-2. 완료 기록 형식

```markdown
| C-N | [설명] | [의존] | [x] → [구현한 것을 행동 단위로 서술. "~를 추가했다"가 아닌 "~조건에서 ~값이 ~된다"] |
```

## 5. 구현 단계 규칙

### 5-1. 구현 시작 전 의무 확인

```
C 항목 하나를 구현하기 전:
□ 해당 항목의 의존 리서치 문서를 읽었다
□ 구현에 필요한 모든 값(상수, 조건, 분기)이 리서치 문서에 있다
□ 모든 의존 항목이 [x]이다 (미완료 의존 항목이 있으면 중단)
□ 1.21.1 API 이름이 확인되었다 (미확인이면 A 항목 등록 후 중단)
```

### 5-2. 구현 중 TODO 작성 금지 규칙

> **코드에 `// TODO` 또는 `// [미확인]`을 작성하는 순간, 반드시 동시에:**

```
1. PENDING_RESEARCH.md를 열어 해당 항목을 C 항목 또는 A 항목으로 등록한다
2. 등록하지 않은 TODO는 작성하지 않는다
3. "Phase N에서 구현"은 Phase N에 해당하는 C 항목이 등록된 경우에만 허용된다
```

**Phase 태그 사용 규칙:**
```
허용: // Phase 13에서 구현 — PENDING_RESEARCH.md C-23에 등록됨
금지: // TODO Phase 13 (C 항목 없이 Phase 태그만 있음)
금지: // TODO — 나중에 (추적 항목 없음)
```

### 5-3. 메서드 바디 비워두기 금지

```
금지 패턴:
  public void tickEssential() {
      // TODO Phase 5
  }

이 코드를 작성하면:
  1. PENDING_RESEARCH.md에 C 항목이 먼저 존재해야 한다
  2. 해당 C 항목에 "tickEssential() 바디 비어있음 — C-N에서 구현 예정" 명시
  3. 현재 C 항목은 [x] 처리 불가 (메서드가 비어있으므로)
```

### 5-4. no-op 핸들러 금지

```
금지 패턴:
  (payload, context) -> { /* 미확인 */ }

대신:
  - 동작이 확인되면 구현한다
  - 동작이 미확인이면 A 항목에 등록하고, 해당 C 항목을 [x]로 처리하지 않는다
  - 원본에서 실제로 no-op인 경우에만 주석으로 "원본도 no-op — [확인됨]" 명시
```

### 5-5. 임시값/근사값 사용 규칙

```
금지 패턴:
  float upFactor = 1.0D; // TODO: 기본값 미확인

허용 조건:
  - 임시값을 사용할 경우 반드시 해당 상수의 확인을 A 항목으로 등록한다
  - A 항목이 [x]가 되기 전까지 해당 C 항목은 [x]로 처리할 수 없다
  - 임시값 코드 위에 반드시 "A-N 확인 후 교체 필요" 주석을 달아 추적 가능하게 한다
```

## 6. 완료 정의 (Definition of Done)

### 6-1. C 항목 완료 기준

C 항목을 `[x]`로 처리하려면 **아래 전체를 만족**해야 한다:

```
□ 해당 동작이 코드에 실제로 구현되어 있다 (메서드 바디가 비어있지 않다)
□ 구현 코드 안에 `// TODO`, `// [미확인]`, `// Phase N` 주석이 없다
   - 있다면 해당 주석을 C 항목으로 등록하고, 이 항목과 분리한다
□ 구현에 사용한 모든 상수/값이 리서치 문서에서 확인된 값이다
□ 구현이 의존하는 모든 C 항목이 [x]이다
□ 컴파일이 성공한다
□ 아래 완료 전 검증 체크리스트를 통과한다
```

### 6-2. 완료 전 검증 체크리스트

```
[구현-검증] 이 C 항목의 의존 리서치 문서에서 관련 메서드/분기를 다시 읽었다
[구현-검증] 리서치 문서의 동작 설명과 구현 코드가 1:1로 대응된다
[구현-검증] 리서치 문서에 기록된 모든 분기(if/else)가 코드에 존재한다
[구현-검증] 리서치 문서에 기록된 모든 상수가 코드에 반영되었다
[구현-검증] 구현 과정에서 새로 발견한 누락 항목이 있다면 C 항목으로 등록했다
[구현-검증] 해당 메서드를 호출하는 타이밍(훅 위치)이 원본과 일치한다
```

### 6-3. 리서치 청크 완료 기준

리서치 청크를 완료로 처리하려면:

```
□ 원본 클래스의 모든 메서드가 C 항목으로 변환되었다
□ 각 C 항목은 원자 단위 기준을 만족한다
□ 미확인 항목이 있다면 모두 A 항목으로 등록되었다
□ A 항목이 전부 [x]가 되기 전까지 관련 C 항목은 시작 불가
```

## 7. 미확인(A) 항목 처리 규칙

### 7-1. A 항목 발생 시 즉시 처리

```
A 항목이 발생하는 경우:
  1. 원본 상수값 미확인
  2. 1.21.1 Yarn API 이름 미확인
  3. 원본 동작 방식 미확인

처리 순서:
  1. PENDING_RESEARCH.md A 섹션에 즉시 등록
  2. 관련 C 항목에 "A-N 미확인 — C 항목 시작 불가" 표시
  3. A 항목을 해결하기 전에는 관련 C 항목 구현을 시작하지 않는다
```

### 7-2. A 항목 해결 방법

```
상수값 미확인:
  → docs/research/original/ 에서 원본 소스를 다시 확인
  → 없으면 GitHub SmartMoving 소스 직접 검색

Yarn API 이름 미확인:
  → Fabric Loom 디컴파일 소스에서 직접 확인 (build/loom-cache 또는 IDE 디컴파일)
  → 확인 후 A 항목에 결과 기록

원본 동작 방식 미확인:
  → 원본 클래스의 리서치 문서를 다시 읽어 근거 찾기
  → 없으면 해당 리서치 문서에 추가 기록
```

### 7-3. A 항목 완료 조건

```
□ 확인된 값/이름/동작이 리서치 문서에 기록되었다
□ 임시값이 사용된 코드가 있다면 해당 코드가 확인된 값으로 교체되었다
□ 관련 C 항목의 "미확인" 블록 해제 표시
```

## 8. 누수 감지 절차

매 N개의 C 항목 완료마다 아래 누수 감지 절차를 실행한다.

### 8-1. 코드 내 TODO 스캔

```bash
# 추적되지 않는 TODO를 찾는다
grep -rn "// TODO" src/
grep -rn "// \[미확인" src/
grep -rn "Phase [0-9]" src/
```

결과에서 PENDING_RESEARCH.md에 대응 C 항목이 없는 것이 있으면:
→ 즉시 C 항목 또는 A 항목으로 등록한다

### 8-2. 빈 메서드 스캔

```bash
# 바디가 비어있는 메서드 탐색
grep -rn "public void.*{$" src/   # 단일 행 빈 메서드
```

### 8-3. no-op 핸들러 스캔

```bash
grep -rn "-> {}" src/
grep -rn "/\* no" src/
grep -rn "/\* TODO" src/
```

### 8-4. 리서치 문서 대조 체크

구현 완료 주장하는 클래스가 있으면:
```
1. 해당 클래스의 리서치 문서를 연다
2. 리서치 문서의 메서드 목록을 만든다
3. 실제 구현 파일의 메서드 목록을 만든다
4. 리서치 문서에는 있는데 구현 파일에 없는 것 → 즉시 C 항목 등록
```

## 9. 금지 패턴 목록

아래 패턴이 코드에 나타나면 즉시 처리해야 한다.

```java
// ❌ 추적 없는 TODO
```

## 10. 전체 작업 흐름 (정상 경로)

```
[단계 1] 원본 클래스 선정
    └─ 어떤 클래스를 포팅할지 결정

[단계 2] 리서치 문서 작성
    └─ 원본 소스 전체를 읽으며 모든 메서드/분기/상수 추출
    └─ 미확인 항목은 A 항목으로 등록
    └─ 리서치 완전성 기준(3-1) 통과 확인

[단계 3] A 항목 해결
    └─ 리서치에서 발생한 미확인 항목 전부 해결
    └─ A 항목이 전부 [x]가 되어야 다음 단계 진행

[단계 4] C 항목 등록
    └─ 리서치 문서를 원자 단위로 분해하여 C 항목 등록
    └─ 항목당 원자 동작 하나 기준(3-3) 준수

[단계 5] C 항목 구현 (하나씩)
    └─ 구현 전 의무 확인(5-1) 통과
    └─ 구현 중 새 TODO 발생 → 즉시 C/A 항목 등록(5-2)
    └─ 완료 전 검증 체크리스트(6-2) 통과 후 [x]

[단계 6] 누수 감지 스캔 (매 5~10개 C 항목마다)
    └─ 코드 TODO 스캔(8-1)
    └─ 빈 메서드 스캔(8-2)
    └─ 리서치 문서 대조(8-4)
    └─ 발견된 누락 → C 항목 등록 후 단계 5로

[단계 7] 클래스 완료 선언
    └─ 해당 클래스의 모든 C 항목 [x]
    └─ 누수 감지 스캔 통과
    └─ 코드 내 TODO/[미확인] 제로
```

## 11. 특수 상황 처리

### 11-1. "원본에 없는 것을 1.21.1에서 추가해야 하는 경우"

```
예: 1.7.10에는 EntityPose가 없었지만 1.21.1에는 필요함

처리:
1. C 항목 설명에 "[1.21.1 추가]" 태그를 달아 원본과 구분
2. 추가 이유를 리서치 문서에 기록
3. 원본에 없는 코드가 원본 동작을 망가뜨리지 않는지 확인
```

### 11-2. "원본 동작을 1.21.1에서 정확히 재현 불가한 경우"

```
예: ModelRotationRenderer의 비표준 회전 순서 → 1.21.1에서 완전 재현 불가

처리:
1. 리서치 문서에 "완전 재현 불가 — [이유]" 기록
2. 최대한 근사한 구현 + "원본과 차이 있음 — [차이 설명]" 주석
3. C 항목 완료 기록에 "근사 구현 — [차이 설명]" 명시
4. "완전히 동일하다"고 기록하지 않는다
```

### 11-3. "리서치 문서가 불완전하다고 판단될 때"

```
처리:
1. 원본 소스를 다시 열어 해당 부분 재확인
2. 리서치 문서를 업데이트
3. 새로 발견된 항목 → C 항목 등록
4. 이미 [x]로 처리된 C 항목에 영향이 있으면 → 해당 C 항목 재오픈
```

## 12. PENDING_RESEARCH.md 관리 규칙

```
A 항목 섹션: 원본 동작 미확인 / 1.21.1 API 미확인
B 항목 섹션: 1.21.1 vanilla 동작 미확인
C 항목 섹션: 구현 항목 (원자 단위, 하나씩 진행)

규칙:
- C 항목은 의존 항목(A/B/C)이 모두 [x]인 것부터 시작
- C 항목 완료 시 완료 기록을 상세히 남긴다 (무엇이 어떻게 동작하는지)
- 완료 기록이 없는 [x]는 검증 불가 → 재오픈 가능
- 월 1회 이상 grep 스캔(8-1~8-3)으로 추적되지 않는 TODO 감지
```

# 리서치 규칙

이 프로젝트의 모든 리서치는 아래 규칙을 100% 준수해야 한다.
규칙을 하나라도 어기면 그 리서치는 무효로 간주한다.

---

## 핵심 원칙

**추정 금지. 확인만.**
**예외 없음. 최소 기준 없음. 모든 파일, 모든 코드.**

이 작업은 1:1 번역이다.
원본의 모든 코드를 완전히 이해한 뒤, 그것을 1.21.1 Fabric으로 번역하는 것이다.
"관련 없어 보이는 파일", "작은 파일", "유틸리티 파일" — 전부 읽는다. 예외 없다.

"~일 것이다", "~인 것 같다", "~라고 생각한다"는 리서치 문서에 절대 쓰지 않는다.
모든 내용은 실제 코드를 직접 읽고 확인한 것만 적는다.

---

## 규칙 1 — 원본 소스 리서치 (SmartMoving + SmartRender)

### 1-0. 읽어야 하는 원본 소스

원본은 두 개의 별도 모드로 구성된다. **둘 다 모든 파일을 전부 읽는다.**

| 모드 | 소스 위치 |
|------|-----------|
| SmartMoving | https://github.com/makamys/SmartMoving |
| SmartRender | https://github.com/makamys/SmartRender |

읽어야 할 파일 목록은 `PROGRESS.md`에 전체가 나열되어 있다.
그 목록이 전부다. 추가로 빠진 파일이 있으면 목록에 추가한 뒤 읽는다.

### 1-1. 읽는 방법

- 파일을 열어서 **첫 줄부터 마지막 줄까지** 읽는다.
- 모든 메서드, 모든 필드, 모든 조건식을 읽는다.
- "이 파일은 별로 중요하지 않겠지"라는 판단을 하지 않는다.
- "대충 파악했다"는 완료가 아니다. 코드를 전부 읽고 이해한 것만 완료다.
- 완료한 파일은 `PROGRESS.md`에서 체크하고 즉시 커밋한다.

### 1-2. 모든 파일에서 추출할 항목

- **역할**: 이 클래스/메서드가 하는 일
- **실행 위치**: 서버 / 클라이언트 / 양쪽
- **호출 시점**: 어디서, 어느 순서로 호출되는지
- **모든 수치**: float/double 상수, 조건 임계값 전부
- **모든 조건식**: 상태 전환 조건, if문 조건 전부 (코드 그대로)
- **의존 관계**: 다른 클래스/메서드/필드에 무엇을 의존하는지
- **계층 구조**: 1.7.10 모델의 부모-자식 관계 (bipedOuter→bipedTorso→팔/다리 등)
- **모드 간 호출**: SmartMoving ↔ SmartRender 간 호출 관계

### 1-3. 기록 형식

```
[모드명 / 클래스명.메서드명]
- 역할: (한 줄)
- 실행 위치: 서버 / 클라이언트 / 양쪽
- 호출 시점: (어디서 호출되는지)
- 핵심 로직: (코드 스니펫 그대로)
- 의존하는 것: (다른 상태, 필드, 메서드)
```

## 규칙 2 — vanilla Minecraft 1.21.1 Fabric 리서치

### 2-1. 실제 소스를 읽는다

- Fabric Loom이 제공하는 디컴파일 소스를 직접 읽는다.
  - 경로: `~/.gradle/caches/fabric-loom/1.21.1/minecraft-common.jar` (디컴파일)
- "MC는 이렇게 동작할 것이다"는 추정을 쓰지 않는다.
- 메서드 이름은 반드시 **Yarn 매핑 기준**으로 확인한다.
  - Mojmap 이름(`getEntityPose` 등)을 Yarn 이름으로 착각하는 실수 금지.
  - 확인 방법: `~/.gradle/caches/fabric-loom/1.21.1/net.fabricmc.yarn.*/mappings.jar` 안의 `mappings/mappings.tiny`에서 직접 검색.

### 2-2. 추적 방법

우리가 간섭하는 모든 vanilla 코드 경로를 **진입점부터 끝까지** 추적한다.
중간에 "여기서부터는 알겠다"고 생략하지 않는다.
추적 대상 목록은 `PROGRESS.md`에 있다.

### 2-3. 추출할 항목

- **실제 메서드 시그니처** (Yarn 이름, 파라미터 타입 — mappings.tiny 확인 필수)
- **실행 순서**: 한 틱 안에서 메서드들이 호출되는 정확한 순서
- **모든 조건 분기**: if문 조건식 그대로
- **모든 수치**: 하드코딩된 상수, lerp 계수 등
- **서버/클라이언트 구분**

### 2-4. 기록 형식

```
[클래스명.메서드명 (Yarn명 확인됨)]
- 실행 위치: 서버 / 클라이언트 / 양쪽
- 호출 시점: (어디서, 어느 순서로)
- 실제 코드: (전체 또는 핵심 부분, 추정 없이)
- 우리와의 충돌 가능성: (있으면 구체적으로 / 없으면 "없음")
```

## 규칙 3 — 교차 분석

원본의 **모든** 기능에 대해 1.21.1과 1:1로 대응시킨다.

- 1.21.1에서 동일한 역할을 하는 vanilla 코드가 무엇인지
- 우리가 어느 지점에 어떤 방식으로 끼어들어야 하는지
- 끼어들 때 vanilla의 어떤 동작과 충돌하는지 (충돌 가능성이 있으면 전부)

충돌은 "충돌할 것 같다"가 아니라,
"이 vanilla 코드가 이 조건에서 이 값을 변경하는데, 우리 코드도 같은 값을 변경하므로 충돌"
처럼 코드 기반으로 구체적으로.

미확인 항목은 `[미확인 — 이유]`로 표시한다. 미확인 항목이 있는 채로 구현 시작 금지.

## 규칙 4 — 리서치 문서 구조

```
docs/research/
  RESEARCH_RULES.md           ← 이 파일
  PROGRESS.md                 ← 전체 진행 체크리스트
  original/
    smartmoving/
      <파일명 또는 시스템명>.md
    smartrender/
      <파일명 또는 시스템명>.md
  vanilla/
    <시스템명>.md
  mapping/
    <시스템명>.md              ← 원본↔1.21.1 교차 분석 + 구현 설계
```

하나의 리서치 파일이 "완료"되는 조건:
- 해당 파일/시스템의 **모든 코드**가 읽혔음
- 미확인 항목이 없음
- `PROGRESS.md` 체크 완료 + 커밋 완료

이 조건을 충족하지 않으면 "완료"라고 쓰지 않는다.

기존 `docs/research_*.md` 파일들은 이 규칙을 따르지 않은 불완전한 리서치다.
새 리서치 결과와 충돌하면 새 리서치를 우선한다.

## 규칙 5 — 구현 시작 조건

다음 조건이 모두 충족되어야 해당 시스템의 구현을 시작한다:

- [ ] SmartMoving 관련 파일 전체 리서치 완료
- [ ] SmartRender 관련 파일 전체 리서치 완료
- [ ] vanilla 1.21.1 관련 코드 경로 전체 리서치 완료
- [ ] 교차 분석 + 충돌 지점 전부 식별 완료
- [ ] 미확인 항목 없음
- [ ] 구현 방법 확정 (코드 근거 있는 방법으로)

위 조건 없이 "일단 구현하고 보자"는 금지.

---

## 금지 사항

| 금지 | 이유 |
|------|------|
| 파일 일부만 읽기 | 1:1 번역 작업이다. 모든 코드를 읽어야 한다 |
| "이 파일은 중요하지 않겠지" | 그 판단 자체가 추정이다. 읽기 전까지 모른다 |
| SmartRender 생략 | 애니메이션 실제 로직이 여기 있다 |
| "~일 것이다" | 확인되지 않은 것을 사실처럼 쓰면 구현이 틀린다 |
| Mojmap 이름 사용 | Yarn과 다를 수 있다. mappings.tiny에서 확인 |
| 미확인 항목 있는 채로 구현 | 구현 중 발견하면 처음부터 다시 |
| 기존 research_*.md 재탕 | 이 규칙을 안 지킨 리서치는 신뢰하지 않는다 |
